## EXECUTIVE SUMMARY

The TATI MVP currently has two interconnected strategic opportunities:

1. **H5.2 — Provisioned Pilot Model**: Replace parent self-signup with admin-provisioned accounts
2. **Lovable Exit**: Remove Lovable as a runtime dependency (currently used for Vite config and asset CDN fallback)

This audit maps both dependencies before any implementation changes.

## PART A — BASELINE ARCHITECTURE AUDIT

### A.1 AUTHENTICATION

#### Parent Authentication (Current)
- **Entry**: `src/routes/(public)/signup.tsx` and `src/routes/(public)/login.tsx`
- **Method**: Firebase Auth (email/password + Google OAuth)
- **Session**: HTTP-only cookie (`parent-session` dev / `__Secure-parent-session` prod)
- **Duration**: 5 days
- **Server Verification**: `getCurrentParentContext()` in `src/lib/backend/firebase/parent-auth.server.ts`
  - Verifies session cookie via `auth.verifySessionCookie()`
  - Returns `{uid}` from authenticated parent
- **Key Function**: `createParentSessionFn()` — Creates session after login/signup

#### Child Authentication (Current)
- **Entry**: `src/routes/child/login.tsx` — TATI ID + PIN
- **Lookup**: Supabase `child_profiles` table → `tati_id` field
- **Session**: Firestore session document + HTTP-only cookie
- **No parental involvement**: Children authenticate directly via credential, not through parent context

#### Admin & Facilitator (Current)
- **Admin Dashboard**: `src/routes/admin/` (minimal, not production-grade)
- **Facilitator Auth**: `src/lib/auth/facilitator-auth.functions.ts` (Firebase UID based)
- **School Admin**: Firestore path `/schools/{schoolId}/admins/{uid}`
- **Gaps**: 
  - Admin routes not explicitly protected by Firestore rules
  - No formal provisioning workflow

### A.2 PARENT ONBOARDING (CURRENT FLOW)

**Step-by-Step**:
1. Parent visits `/signup`
2. Creates Firebase Auth user (email/password or Google)
3. Redirected to `/onboarding` → Child profile creation form
4. Collects: child name, age (8-12), avatar emoji
5. Creates child in `families/{familyId}/children/{childId}`
6. Sets `onboardingCompleted: true`
7. Navigates to child pre-assessment

**Family Initialization**:
- Automatic via `ensureFamily()` in `FirebaseFamilyRepository`
- Creates `families/{uid}` doc with parent as member
- Idempotent (called every time, but only creates once)

**Child Credential Generation**:
- **Current Issue**: TATI ID + PIN generation happens during `createChild()` via `generateChildCredential()`
- **Location**: `src/lib/backend/firebase/repositories.ts` → `FirebaseFamilyRepository.createChild()`
- **Storage**: `childCredentials/{childId}` Firestore doc
- **PIN**: Stored as SHA-256 hash

### A.3 ADMIN SYSTEM (EXISTING BUT MINIMAL)

**Admin Dashboard Location**: `src/routes/admin/index.tsx`

**Current Capabilities**:
- Tabs: overview, users, schools, facilitators, families
- Query users, schools, families from Firestore
- Display collections without modifying

**Current Limitations**:
- No user provisioning workflow
- No parent/family creation server functions
- No child credential generation for admin
- Not protected by explicit authorization checks
- Parents still self-signup

**Gap**: H5.2 requires building formal admin provisioning for pilot.

### A.4 FIRESTORE DATA MODEL

**Collections**:
```
users/{uid}
  → Parent/facilitator/admin profiles
  
families/{familyId}
  → Family document (displayName, createdAt)
  → members/{uid} → Family membership (parent)
  → children/{childId} → Child profile (name, age, avatar, tati_id, onboardingCompleted)
  
childCredentials/{childId}
  → tati_id (string)
  → pin_hash (SHA-256)
  
schools/{schoolId}
  → School data
  → admins/{uid} → School admin assignment
  
child_sessions/{sessionId} (Firestore backup of session tokens)
```

**Key Observations**:
- Parent UID derived from Firebase Auth (no self-assigned)
- Child TATI ID + PIN stored in separate `childCredentials` collection
- Family membership is explicit (via `/members/{uid}`)
- Child isolation: RLS rules ensure child can only access own profile/progress

### B.7 /__l5e/ MIDDLEWARE ANALYSIS

**Current Implementation** (`src/server.ts`):
```typescript
if (isDevelopment) {
  const url = new URL(request.url);
  if (url.pathname.startsWith("/__l5e/")) {
    return handleAssetRequest();  // Returns placeholder PNG
  }
}
```

**Behavior**:
- **Development**: Returns light gray 1×1 placeholder PNG (76 bytes)
- **Production**: Passes through to Lovable CDN (NOT production-safe for exit)

**What Generates Requests**:
- Component imports: `import x from "@/assets/x.png.asset.json"`
- Asset JSON files contain URL: `/__l5e/assets-v1/[asset-id]/[filename]`
- React renders `<img src={assetJson.url} />`

**Issue**: Production still depends on Lovable CDN. This middleware only masks the problem in development.

## PART D — H5.2 PROVISIONING MODEL DEPENDENCIES

### D.1 CURRENT STATE (Parent Self-Service)

```
Parent visits TATI
  ↓
/signup → Firebase Auth (creates account)
  ↓
/onboarding → Manual child entry (name, age, avatar)
  ↓
Child created with auto-generated TATI ID + PIN
  ↓
Parent sees child in /parent dashboard
```

### D.2 H5.2 TARGET STATE (Admin-Provisioned)

```
TATI Admin provisions parents/families/children
  ↓
Parent receives email with login credentials
  ↓
Parent logs into /parent dashboard
  ↓
Parent sees assigned children (no onboarding)
  ↓
Child logs in with TATI ID + PIN
  ↓
Child begins learning journey
```

### D.3 REQUIRED H5.2 FEATURES

**Admin Provisioning Workflow**:
1. Admin login (protected)
2. Create parent account (Firebase Auth programmatically)
3. Create family
4. Create child profile
5. Generate TATI ID + PIN
6. Optionally: Assign to school/cohort

**Parent Changes**:
- `/signup` → Disabled or removed (no self-signup)
- `/login` → Unchanged (Firebase Auth still works)
- `/parent` → Unchanged (shows assigned children)
- `/onboarding` → Removed (no child creation UI)

**Child Changes**:
- `/child/login` → Unchanged (TATI ID + PIN)

### D.4 DEPENDENCIES BETWEEN H5.2 AND LOVABLE EXIT

**Independent**:
- H5.2 provisioning model is independent of Lovable
- Can implement H5.2 with Lovable still present (or after exit)

**Related**:
- Both simplify TATI infrastructure
- Both improve security (no self-service account creation)

**Recommendation**: Exit Lovable first (simpler, isolated), then implement H5.2 (builds on clean foundation).
